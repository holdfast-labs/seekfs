# Content accent folding design

## Current behavior (content)

- Build: `contentTokenizeDocForBuild` repairs source text, calls `contentFoldText`, then builds dictionary terms with `contentTermsOfFolded` and byte trigrams with `contentGramsOfU32` (`cmd/seekfs/content_build.go:575-587`). The assembler emits those terms and grams and derives each per-file bloom row from the same gram set (`content_build.go:768-783`). `contentFoldText` is Unicode lowercase only (ASCII fast path) (`content_build.go:1088-1117`); source text remains case-preserving for v11 disk verification.
- Query candidates: `contentCandidatesBounded` folds term/phrase leaves with `contentFoldText` before trigram posting lookup (`content_verify.go:1103-1109`; OR alternatives at `1327-1331`). Regex required runs are lowercased, not accent folded, before candidate lookup (`content_verify.go:1274-1314`).
- Per-file filter: ordinary query needles and bloom grams use `contentFoldText` (`content_verify.go:257-275`); regex candidate/filter required-run grams are built from lowercased extracted literals (`content_verify.go:198-254`). Filter gate checks those bits before disk reads (`content_verify.go:559-624`); builder bits correspond to the build grams (`content_build.go:776-783`, `content_filter.go:78-99`).
- Verify: the matcher lowercases term/phrase needles (`content_verify.go:413-421`) and the haystack (`content_verify.go:424-433`); lazy per-entry matching folds text in `matchRawFirst` (`content_verify.go:470-513`). Regex compiles with `(?i)` for default case-insensitivity (`content_verify.go:190-205`) and runs against raw text (`content_verify.go:435-467`); Go regexp case-folding does not remove accents. Snippets reuse the matcher/needle and folded haystack (`content_verify.go:851-909`), with offset mapping helpers assuming one-to-one rune folding (`content_verify.go:805-839`).
- `--lines` uses the same lowercase-only fold on each line (`content_lines.go:78`); term/phrase matching then checks the folded line and regex uses its case-insensitive regex path. Thus accent-insensitive support must include it, not just service search.

## Approaches

| Approach | Terms / phrases | Substrings | Regex | Index size | Query cost | Rebuild |
|---|---|---|---|---|---|---|
| A. Accent-fold at build (terms, grams, filter) and verify | Correct with matching query transform. | Correct when haystack and query share the same normalized folded bytes. | Could work for literals only if regex is parsed/transformed into folded semantics; ordinary `(?i)` on raw bytes remains accent-sensitive. | Usually dictionary/gram count contracts for Latin accents, but fold collisions combine postings; per-file Bloom density may rise. | Cheapest candidates and verification; one shared fold at build/query. | Format bump + full content rebuild; expensive CPU and disk I/O, particularly owner's large drive. |
| B. Keep index; expand query through term dictionary | Whole-token term queries can union original/fold-equivalent terms, then verify. | Not complete: an unaccented query's trigram bytes do not occur in accented text's indexed grams; scanning all candidates is needed. | Regex semantics cannot be supplied by term-dictionary expansion; literal runs still need candidate superset and raw regex verification. | None. | Dictionary scans / variant unions; potentially many candidates and disk verification. Correct substring support means broad scan, high cost. | None; existing sidecars stay valid. |
| C. Hybrid: retain v11 index, fold verification and compensate candidate/filter lanes | Exact token candidates are broadened by dictionary scan/variant union, verified accent-insensitively. | Fall back to broad candidate scan when folded query grams are not sound against existing indexed grams (or use full scan for accent-sensitive mismatch cases). | For correctness, regex verification needs accent-aware regex semantics (transform supported literals or evaluate over a folded view); candidate extraction must be a safe superset, else scan. | None. | Cheap where a sound posting superset exists; potentially expensive scans on accent-changing queries. More branch complexity and worst-case disk reads. | None, but hybrid logic has continuing complexity/cost.

`contentIndexVersion` is currently 11 (`cmd/seekfs/content_index.go:120`). Its reader rejects nonmatching versions in `contentIndexDecode` (`content_index.go:618-626`); the v11 header documents version mismatch as fail-closed so service rebuilds, and explains v10-to-v11 changes (`content_index.go:100-117`). Prior v9->v10 and v10->v11 rationale is documented there; v11 also changes filter and content storage semantics. Any build-side normalization change must bump the version and rely on this existing reject/rebuild behavior, never attach old gram/filter sections as current.

## Recommendation: C, query/verification-side accent folding, retain v11 format

Use `foldAccentLower` from `cmd/seekfs/fold.go:37-57` as the canonical Unicode NFD + strip `Mn` + fullwidth-fold + lowercase transform (already used for names). This is script-general Unicode normalization, not Latin-only: stripping `Mn` can alter meaning in scripts where marks are lexical, so explicitly constrain the first implementation to Latin-script accent marks, or decide that this existing name-fold behavior is the intended broader policy before reuse. Preferred initial contract: Latin accents only; preserve non-Latin combining marks. Handle precomposed Latin letters through NFD. Name search's “smart” behavior is the appropriate content rule: default case-insensitive query, an unaccented letter folds and matches accented/unaccented forms, while an accented query remains exact for that letter (accent-bearing query takes its literal lane and is not broadened). `case:true` remains exact case and accent. This balances convenient ASCII queries with user intent for a specifically accented spelling.

Do not alter persisted terms, grams, or filter rows: that would demand a format bump and whole-drive rebuild, while v11 verifies from disk and search cost is already disk-bound. For all accent-capable content queries, avoid using incompatible old trigrams/filter bits as a rejecting gate: choose a candidate superset by scanning relevant records (or create a new in-memory Unicode-folded view only when measured worthwhile); verify exact results against folded text. Keep raw text for snippets and map folded byte spans back to raw via an explicit offset map, since NFD/mark removal changes rune and byte counts; update `--lines` likewise. For regex, preserve syntax and fold only literal runs / evaluate regex over a transformed view with source-offset mapping; if safe transformation is unavailable, use raw regex semantics rather than false negatives and document the limitation. Avoid simply applying `(?i)` to a folded haystack, which changes regex character classes/escapes.

Likely change sites: `content_verify.go` matcher construction, term/phrase verify, candidate selection, and filter gate; `content_filter.go` query-side filter gram derivation (or disable gate for accent-aware cases); `content_lines.go` line fold/match; `content_build.go` unchanged for persisted form; `content_index.go` unchanged. Reuse fold logic but introduce a content-specific Latin-aware transform if limiting marks, so filename semantics are not silently changed. Tests to add: `TestContentAccentFoldTermAndPhrase`, `TestContentAccentFoldSubstringFallback`, `TestContentAccentFoldSmartAccentQuery`, `TestContentAccentFoldCaseTrue`, `TestContentAccentFoldRegex`, `TestContentAccentFoldSnippetRawSpan`, `TestContentAccentFoldLines`, and `TestContentAccentFoldFilterNoFalseNegative`; include NFC/NFD inputs, `café`/`cafe`, non-Latin marks, and short (<3 byte) queries. Estimated product diff: 6-9 files, roughly 250-450 LOC plus tests; no format/rebuild work. A's diff likely 150-250 LOC but mandatory version/rebuild path; B 200-350 LOC and still incorrect for substrings without scans.
